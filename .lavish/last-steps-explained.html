Explained simply

What we're actually building, and why

A way to answer one question with evidence: which model, for which kind of task, and where does it break? Not “how smart is it” — where does its ability stop?

The big idea, in one line

Give it a fixed task and one variable input; it grades the result on four axes and reports where the axes disagree.

The variable is usually which model wrote the code. That's just the first knob we turned. The same machine can sweep a prompt, an instruction file, or a retrieval setting. More on that at the bottom.

The problem: one score hides the interesting part

Almost every benchmark asks one question — “did it pass the tests?” — and prints one number. That number is like a driving test that only checks parking. It hides the cases that actually matter:

Passes, but misses the point

Green tests, wrong behaviour. The tests only assert what they assert.

Works once, breaks on edges

Fine for the obvious input, fails the moment reality shows up.

Right, but unreadable

Correct and painful to own. A one-number score can't show this.

The insight: those are three different failures. Collapsing them into one score erases exactly the information you'd need to act on.

Our approach: score separately, then look at the gaps

Instead of one number, every answer gets four independent marks — and we deliberately don't add them up first. The disagreements are the product.

✳ Only semantic is an opinion. That distinction is the whole of the second fix, below.

Why four marks work

Each mark uses a different, independent source: two hidden test suites, a judge, and a rule-based checker. Because they don't share a source, a gap between them is a real signal, not noise.

Why a fixed task matters

Everyone gets the exact same task and the exact same hidden tests. That's what makes two answers comparable. The reference answer stays hidden from the model under test.

The last few steps

Two bugs that both looked like results

Both had the same shape: a failure was quietly rendered as a confident number. That's the dangerous kind — it looks like a finding.

Fix 1 — harness vs model

A robot that froze and a robot that wrote bad code both scored 0.0 — so a freeze was read as “bad at coding.” One real race looked like a 0.11 gap; without the freezes it was 0.03, a tie. The “finding” was a broken harness.

Fix: label every try (scored / timeout / provider_error / unparseable_output), exclude infrastructure failures from every average, retry once, and stamp the run UNRELIABLE if too many tries weren't real measurements.

Fix 2 — opinion vs measurement

The judge was asked for a score out of one with nothing to compare against, so it invented a scale every time — and its opinion was blended into the overall mark at a quarter of the weight, as if it were a measurement.

Fix: show the judge the task's reference answer and ask it to compare; give concrete 1.0 / 0.5 / 0.0 examples; and take the opinion out of the overall mark, reporting it in its own, clearly-labelled column.

Said plainly: both fixes change what every earlier number meant. Old reports stay on disk as history, marked “historical,” and are not comparable with new runs — the freezes were counted as zeros, and the opinion was mixed into the average. Re-running quietly would have been the dishonest option.

Is this only for grading Python programs?

No — and this is the part worth being precise about. The architecture generalises; the task library does not.

What generalises for free
  • The four axes (run it, stress it, judge it, check its form)
  • The idea of sweeping one variable and grading the output
  • Disagreement detection and the two safeguards
  • The reporting shape: strengths, weaknesses, and disagreement
What every new target needs
  • New tasks written for that target
  • A hidden test suite (or a mechanical check) for each
  • A reference answer to anchor the judge

Writing those tasks is the work.

Where it fits cleanly — and where it doesn't

fits well

SQL generation, regex/parsers, shell scripts — all runnable and testable.

partly

Infrastructure-as-code — “run it” becomes “validate/plan”, and edges get fuzzy.

not this

Agent behaviour is a trajectory, not code — it needs new axes entirely.
