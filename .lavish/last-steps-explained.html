Explained simply

What we're actually building, and why

A way to answer one question with evidence: which model, for which kind of task, and where does it break? Not “how smart is it” — where does its ability stop?

The whole pipeline

How a run actually flows

One pass, left to right. The same fixed task goes to every model; each answer is graded on the same four axes; the scores are checked for honesty; a report comes out. The two red boxes are the two bugs and where their fixes now sit.

So why the overall mark and the guards?

Fair question — both look like extra steps bolted on. Each exists to stop a specific lie, and the guards exist because of the two bugs.

Overall mark
So people can compare at a glance — safely

Four separate marks are the useful thing, but nobody can hold four numbers in their head across five models. The overall mark is a single sortable number for ordering and for the headline.

It is built only from the three measured axes. The judge's opinion is deliberately left out — an opinion folded into a number is exactly the bug we just fixed. So the overall mark answers “does it work, survive, and read well”, and you read the opinion column separately.

Guards
Because a run can't tell you anything

A number that looks authoritative but measured nothing is worse than no number, because people quote it. Two things make a run meaningless, and each gets its own guard:

  • Degenerate: every model scored identically — the corpus failed to separate them. Ranking from that would be fabrication.
  • Unreliable: too many tries weren't real measurements (timeouts, crashes). The scores that remain may be fine, but the run isn't trustworthy.

They are separate because they mean different things: one says “the test didn't discriminate”, the other says “the test didn't run properly”. When either fires, the results are still written, but the run is stamped INCONCLUSIVE or UNRELIABLE and the tool exits non-zero.

Both guards are scars from real mistakes. The degenerate guard exists because “all 100%” and “all 0%” are the two ways a benchmark lies. The unreliable guard exists because three timed-out tries once made one model look worse than it was — and that became a headline before anyone noticed.

Two things you asked about

Deferred on purpose
The 30 minutes I asked for

A human spot-check: you read ~20 judge verdicts and mark whether you agree. It is the only measurement that answers “is the judge actually right” — two AI judges agreeing just means they don't disagree with each other.

It was deliberately deferred, in writing, for one reason: there's no point paying a human to validate a judge that was known to be badly designed. Anchor it first, then validate. It is now anchored, so this is the natural next change — and it is the strongest thing missing from the trust story.

Good question
Does the judge see bad examples?

No — and it's worth being precise about what it does see. The prompt contains exactly one example: the task's reference answer (a good one), plus written definitions of what 1.0 / 0.5 / 0.0 mean.

So the three bands are defined but only the 1.0 band is illustrated. We do not hand the judge a worked 0.5 or 0.0 candidate to imitate.

Is that required? Not strictly — the definitions may be enough, and the two judges agreed 100% at 1.0. But the honest answer is that a worked bad example might sharpen the low bands, and we don't know because it hasn't been tested. That's a real open question, not a settled design.

Two words worth pinning down first

Almost everything else follows once these are clear.

Corpus
The fixed set of tasks

A folder per task on disk. Each holds the prompt, a hidden ground-truth test file, a hidden edge-case test file, and a reference solution — the answer the author accepts as correct.

Right now: corpus/, 20 tasks. It is the part that does not generalise — a new target needs new tasks written.

Model bank
The contenders being compared

The list of models that take the corpus. This is the thing you vary: point it at four models and you are ranking models; point it at four prompts and you are ranking prompts.

Right now: four reachable through OpenCode, one through Claude Code.

How the two fit together: the corpus is the fixed exam paper; the model bank is who sits it. Same paper for everyone is the whole point — it is what makes two answers comparable.
Vocabulary

What “anchored” means

I keep saying the judge is “anchored to the reference”. That word is doing a lot of work, so here it is plainly.

Unanchored
“Just rate it 0 to 1”

Hand a judge an answer and ask for a score. It has no fixed point to measure against, so it invents one each time. The same answer can come back as 0.8 on Monday and 0.6 on Tuesday — not because it changed, but because the ruler did.

Anchored
“Compare it to this answer”

Give the judge a known-good answer — the task's reference solution — and ask whether the candidate is equivalent, partly there, or wrong. The reference is the fixed point. The ruler is nailed down before measuring starts.

The everyday version: asking “how tall is that tree?” gets an invented number. Asking “is that tree taller than this lamp post?” doesn't. The lamp post is the anchor. Here, the reference answer is the lamp post — and it is only shown to the judge, never to the model being tested. (This is why pairwise benchmarks like MT-Bench and AlpacaEval beat absolute-score ones.)
What anchoring does not fix: it stops the judge drifting, but it doesn't prove the judge is right. If the anchor itself is odd, or the judge misreads it, the number is still wrong — just wrong consistently. That's why the human spot-check matters.
Vocabulary

So what is our anchor, and how did we get it?

Short answer: we didn't choose it — it was already there. The anchor is the solution.py in each corpus folder: the reference answer the task author wrote when they wrote the task.
In your words — two halves
  1. The answer we wrote at the start — which the model never sees while answering — becomes the anchor. ✅ Exactly right.
  2. When we send the answer to be judged, we send the reference answer as well as the generated answer. ✅ Correct — and worth being precise about two gaps.

The anchor is not introduced at generation time; it is introduced at judging time. So there are two separate people, and only one of them ever sees the reference:

The nuance worth pinning down: only the generated answer travels from the model to the judge. The reference does not come from the model or from a previous cache — it is fetched straight from the corpus folder at judging time. The model and the judge are two different runs, and the model's run has no reference in it at all.

Tasks were authored as “a task + a worked answer + tests” from the start — that is the normal shape of a task folder. Anchoring simply started using the answer that was already sitting in the folder. No new artifact had to be created.

Why it is allowed to be the anchor

  • →It is known-good by construction. The corpus validator runs every reference against its own hidden suites. All 20 pass both suites, and every reference defines every required symbol — verified, not assumed.
  • →It is already the answer of record. It is what the tests were written around, so “equivalent to the reference” is as close to “correct” as this corpus can define.
  • →Showing it leaks nothing. The reference is hidden from the model under test and was always hidden. It is only added to the judge's prompt.
The honest boundary: this is a convenient anchor, not a verified one. It is one author's answer passing one set of tests — not proof that the answer is what the task truly wants. That is exactly why a human spot-check (does a person agree with the judge?) is the next step, and why the design says two-judge agreement is stability, never correctness.

The big idea, in one line

Give it a fixed task and one variable input; it grades the result on four axes and reports where the axes disagree.

The variable is usually which model wrote the code. That's just the first knob we turned. The same machine can sweep a prompt, an instruction file, or a retrieval setting. More on that at the bottom.

For the repo README / a visitor

How to tell someone what this does

Three lengths. Say the short one unless they lean in.

One sentence

“It grades AI-written code four different ways and shows you where the grades disagree.”

One paragraph

Most benchmarks run a model's code through tests and print a single score. That hides the interesting failures — code that passes the tests but misses the point, or works for the obvious case and breaks on the edges. This tool scores each answer on four independent axes (does it run, does it survive edge cases, does it do what was asked, is it readable) and reports where those axes disagree, so you can see how a model fails, not just that it scored lower.

The pitch, for the top of the README

code-gen-evals

A four-dimension evaluation framework for code-generation models. Give a fixed set of tasks to several models, score every answer on execution, edge cases, intent and readability, and report where the dimensions disagree — so you learn which model, for which task, and where it breaks, instead of one number that hides all of it.

The problem: one score hides the interesting part

Almost every benchmark asks one question — “did it pass the tests?” — and prints one number. That number is like a driving test that only checks parking. It hides the cases that actually matter:

Passes, but misses the point

Green tests, wrong behaviour. The tests only assert what they assert.

Works once, breaks on edges

Fine for the obvious input, fails the moment reality shows up.

Right, but unreadable

Correct and painful to own. A one-number score can't show this.

The insight: those are three different failures. Collapsing them into one score erases exactly the information you'd need to act on.

Our approach: score separately, then look at the gaps

Instead of one number, every answer gets four independent marks — and we deliberately don't add them up first. The disagreements are the product.

✳ Only semantic is an opinion. That distinction is the whole of the second fix, below.

Why four marks work

Each mark uses a different, independent source: two hidden test suites, a judge, and a rule-based checker. Because they don't share a source, a gap between them is a real signal, not noise.

Why a fixed task matters

Everyone gets the exact same task and the exact same hidden tests. That's what makes two answers comparable. The reference answer stays hidden from the model under test.

The last few steps

Two bugs that both looked like results

Both had the same shape: a failure was quietly rendered as a confident number. That's the dangerous kind — it looks like a finding.

Fix 1 — harness vs model

A robot that froze and a robot that wrote bad code both scored 0.0 — so a freeze was read as “bad at coding.” One real race looked like a 0.11 gap; without the freezes it was 0.03, a tie. The “finding” was a broken harness.

Fix: label every try (scored / timeout / provider_error / unparseable_output), exclude infrastructure failures from every average, retry once, and stamp the run UNRELIABLE if too many tries weren't real measurements.

Fix 2 — opinion vs measurement

The judge was asked for a score out of one with nothing to compare against, so it invented a scale every time — and its opinion was blended into the overall mark at a quarter of the weight, as if it were a measurement.

Fix: show the judge the task's reference answer and ask it to compare; give concrete 1.0 / 0.5 / 0.0 examples; and take the opinion out of the overall mark, reporting it in its own, clearly-labelled column.

Said plainly: both fixes change what every earlier number meant. Old reports stay on disk as history, marked “historical,” and are not comparable with new runs — the freezes were counted as zeros, and the opinion was mixed into the average. Re-running quietly would have been the dishonest option.

Is this only for grading Python programs?

No — and this is the part worth being precise about. The architecture generalises; the task library does not.

What generalises for free
  • The four axes (run it, stress it, judge it, check its form)
  • The idea of sweeping one variable and grading the output
  • Disagreement detection and the two safeguards
  • The reporting shape: strengths, weaknesses, and disagreement
What every new target needs
  • New tasks written for that target
  • A hidden test suite (or a mechanical check) for each
  • A reference answer to anchor the judge

What you need for a new model
  • It reachable by one of the providers (OpenCode, Claude Code, or an API key)
  • That it is not the judge model — a model may not grade itself
What you do not need
  • New tasks, new tests, or a new reference answer
  • Any change to scoring, the judge, or the guards
Why that is the easy case: the corpus is the fixed exam paper, so a new model is just a new person sitting it. The hard case is changing the paper — a new repo, a new language, a new kind of artifact. That is the section below.
Scaling up

Can it grade code in a real repo or an enterprise codebase?

Short answer: not as it stands, and the blocker is not the engine. Today every task is a self-contained function with a hidden test file and a reference answer. A repo has none of those three things waiting for you. The four-axis machinery transfers; what you must build is a way to turn a repo into tasks.

Three things change the moment the artifact is “a change to a repository” rather than “a function”:

1. The artifact is a diff

There is no single solution.py. The thing to grade is a change against a base revision, not a file.

2. Running it needs the repo

Most code does not run standalone. “Does it pass the tests?” needs dependencies, services, a database, a build.

3. The reference is a commit

The anchor would be the human patch that actually shipped, not a written answer. Often there is no such commit.

What would actually have to be built

NeedWhat it meansSize
Repo-shaped specsA task = a base revision + a requirement + the tests that must pass, not a prompt + one filemedium

Reference as a patchThe anchor becomes the human's merged diff; needs a reason to believe it is rightmedium
Repo-aware styleStyle checks must match this repo's conventions, not the house rules baked into this corpusmedium
ContainmentA model that can edit a real repo is a collaborator, not a subject — it must be jailed to a scratch checkoutlarge

Three ways to point it at a repo

easiest
Carve repo tasks

Pick real functions/files in the repo, write a task + hidden tests for each, and use the existing pipeline unchanged. You get repo-shaped tasks without new machinery — but a person still writes them.

middle
Grade a candidate patch

Give a model the requirement plus the repo, take its diff, apply it in a container, and run the project's existing tests. Reuses the four axes; needs the container and a diff-based specs format.

biggest
Grade live agent work

Let an agent act on the repo and grade the trajectory. But “did it behave sensibly” is a different question with different axes — this is the roadmap's agent-behaviour item, and it is a new tool.

The honest line: the four axes, the anchoring and the two guards all carry over. But “execution” for an enterprise repo means “a container that can build and test it”, and that is the whole project. Until that exists, pointing this at a real codebase grades nothing.
