Plain-English walkthrough

We built a fair test for robot coders

Imagine four robots that can write Python. This project gives all four the same homework, grades each answer four different ways, and writes down where the grades disagree. That's the whole idea.

First: why does this need to exist?

The question we're answering.

🤖

Robots write code now

You type "write me a function that adds two numbers" and an AI writes it. Several companies sell this.

❓

But who's the best one?

Nobody knows how to answer that fairly. Every company says theirs is best.

🧸

The cardboard robot

A fake robot with no AI in it, used to check the machinery works without spending money or needing internet.

It says nothing about any real robot's quality. A development convenience, not a feature.

Think of it like a driving test. A driver who passes the parking test might still crash on the motorway. One score of "passed" tells you almost nothing. You need several tests, and you need to know which one they failed.

And the sharpest framing: this isn't really "rate a robot's coding ability" — plenty of benchmarks do that. It's map where that ability stops. The rating is the byproduct; the failure map is the product.

What we actually built

Four things, in order.

  1. 1

    20 homework questions growing from 15

    Little coding puzzles, from easy (FizzBuzz) to hard (a retry timer, a thread-safe counter). Each one comes with a correct answer, so we can check. You asked to keep the easy ones and add harder ones.

  2. 2

    Four robots to test

    Four AI models, all asked the exact same questions under the exact same conditions — no tools, no hints, temperature 0.

  3. 3

    Four ways to grade each answer

    Did it run? Did it handle weird inputs? Did it do what we meant? Is it tidy code? These are different questions.

  4. 4

    A report that admits confusion

    When the four grades disagree, the report says so instead of averaging them into one tidy lie.

The four grades, in kid terms

Same answer, four separate judges, four scores from 0.0 to 1.0.

1 · Does it work? execution

We wrote tests. We run each robot's answer through them. The robot never sees these tests — only we do. 3 of 4 tests passed → 0.75

2 · Does it survive? edge

A second, harder set of tests with weird inputs — empty lists, zero, negative numbers. Also hidden from the robot, so it can't special-case them.

3 · Does it understand? semantic

A different robot reads the request and the answer and asks: "does this do what was asked?" Never the robot being graded — a model can't mark its own homework. It can say "I don't know" and we record that honestly.

4 · Is it tidy? style

Pure maths — no AI. Are there labels on the parts? Notes explaining what it does? Tidy names? Is any line too long?

The clever bit: when the grades fight

If we averaged everything into one number, we'd lose the most useful information.

Real example from our run

"Passed all the tests… but missed the point"

A robot wrote a rate_limiter. Our tests said 1.0 — perfect. But the judge AI said 0.5 — that's not quite what you asked for.

Both are true. Our tests were too easy. The judge caught it. That gap is the finding.

Real example from our run

"Works fine, but it's a mess"

The same robot's rate_limiter also scored 1.0 for working and 1.0 for understanding — but only 0.60 for tidiness. No labels on the parts, no notes explaining anything.

Correct code a human would groan at. One average score would have hidden it.

Why this matters: if your whole report is 0.87 vs 0.85, you might pick the wrong robot. But if you learn that one is tidier and the other handles weird inputs better, you can pick for your situation.

So the framework works, but our homework was too easy. It's like four brilliant students all getting 98% — the test didn't tell us much about who's really best. The right next step is harder puzzles, not more robots.

The safety net that caught our own mistake

A rule we built in that refuses to give a fake answer.

We added a rule: "if every robot scores exactly the same on every question, say the test failed — don't pretend you ranked them."

It fired twice during building. Once it caught a real bug: a run where every score was silently blank because of a mistake in our own code — and all four "looked" almost identical. The safety net refused to report it as a real result.

All 1.00 → suspicious
All 0.00 → suspicious

                        saved, but flagged
                        and exits with an error

The cheap ones are the most revealing. Pass@k tests whether a robot is reliable or just got lucky once. Contamination answers the most awkward question about the current 15 puzzles: they're famous, so did the robots actually solve them, or just remember them?

"Broader bank" — what I actually meant

The bank is just the list of robots you test. Right now it's four names from the same family, same provider, similar strength. Four cousins tying is not surprising.

A broader bank mixes different labs, different sizes (tiny on-device vs frontier), and different ages. Age alone would separate them.

Why it matters: if four similar robots tie, either the puzzles are too easy or the robots are too alike — and you can't tell which. Drop in one weak, old model on the same puzzles: if it scores badly, the puzzles are fine and the bank was too narrow. That's the control experiment.

✓ Trying a different robot

Yes, and it's the easiest thing in the whole repo. Robots are just names — no code changes at all: 

--models "opencode-go/whatever-you-have"

Two rules: the judge must be a different robot (enforced in code), and the robot must be reachable — either your subscription or an API key.

✗ Creating a new robot

No — and this needs saying plainly. Creating a model is training: data, GPUs, weeks. Nothing here does that. This framework measures robots; it does not make them.

What is possible: build your own thing on top of an existing robot — a tuned variant, a wrapper, an agent — then point it at any compatible endpoint. That's ~30 lines. But that's a product built on a model, not a model.

Could other people use this?

Not yet — and the reason is not the code.

Anyone can clone it and run it in 40 seconds. But that's a repo, not a utility. A utility means someone grades their own model without understanding your code.

What I'd refuse to publish today, and why. The current report shows 0.95 vs 0.98 on four near-identical robots, using a corpus that can't discriminate. Published like that, it invites someone to rank models on noise. A benchmark that looks authoritative and measures nothing is worse than no benchmark, because people quote the numbers.

The engineering to publish is roughly a week. Credibility is the real work — and the corpus is the weak point you're already fixing.

A realistic path, in order

  1. 1 Prove it discriminates — hard specs, pass@k, a broad bank, a real spread. Without this there's nothing worth publishing.
  2. 2 Add an OpenAI-compatible backend — one class, and anyone with any endpoint can use it. Highest leverage single change.
  3. 3 Sandbox execution — a container per run. You cannot responsibly tell strangers to run model-authored code without this.
  4. 4 Publish — to PyPI, one command: --provider openai-compatible --base-url … --models my-model
  5. 5 Write it up — methodology, limitations, a reproduction command.

The reframe: this isn't a product yet, it's a measurement instrument you built for yourself. Instruments get published after they produce a repeatable reading — not before.
